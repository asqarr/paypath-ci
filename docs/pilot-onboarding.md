# PayPath CI first-pilot guide

This guide covers the currently implemented CLI for a limited pilot. The package is **not published to npm**. The pilot uses a maintainer-provided `.tgz` and an isolated Stripe Test Mode account, disposable Supabase project, and a Demo authorization API.

PayPath compares three observed outcomes: Stripe subscription/invoice state, the persisted Supabase subscription and entitlement, and the Demo app's Pro authorization response. It can identify a successful payment with missing access, access left enabled after cancellation, and duplicate webhook business effects when the matching delivery/effect evidence is available. The current CLI does not discover arbitrary customer schemas or configure customer policies.

## Requirements and install

- Node.js 24 or later (`node --version`); the repository `.nvmrc` currently selects Node 24.
- npm, and a PayPath CLI tarball supplied by the pilot maintainer.
- For a real integration scan only: a Stripe **Test Mode** subscription, an isolated Supabase test project with the PayPath schema installed, and the Demo API that reads that same test project's state.

The CLI tarball is not available from the npm registry. A maintainer builds it from the matching source checkout:

```powershell
npm ci
npm run build --workspace @paypath/cli
$packDir = Join-Path $env:TEMP ("paypath-pack-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $packDir | Out-Null
npm pack ./packages/cli --pack-destination $packDir
$tarball = Join-Path $packDir "paypath-cli-0.1.0.tgz"
Test-Path $tarball
```

Transfer that tarball to the pilot developer through an approved private channel. The maintainer should also provide the `pilot-integration.env.example` template through that channel (or another approved private file share); it is stored in the PayPath source checkout at `docs/pilot-integration.env.example`. Save the template as `pilot-integration.env.example` in the root of the **customer application repository** (outside the PayPath monorepo). Install the local tarball from that repository:

```powershell
npm install --save-dev "C:\path\to\paypath-cli-0.1.0.tgz"
npm exec -- paypath --help
npm exec -- paypath --version
```

`--version` prints the package version. The installed binary is `paypath`; it bundles PayPath's internal workspace packages, while npm installs its declared public runtime dependencies. Do not publish or upload a pilot tarball to a public registry.

If you are working in a PayPath source checkout instead of the customer application repository, the template can be copied directly from its repository path:

```powershell
if (Test-Path .\.env.integration.local) {
  throw '.env.integration.local already exists; review it before copying the template.'
}
Copy-Item .\docs\pilot-integration.env.example .\.env.integration.local
```

## Local fixture proof (no external account)

From the application repository where the tarball is installed:

```powershell
npm exec -- paypath test --mode fixed --scenario successful-payment --report .\successful-payment-fixed.json
```

Expected: `PASS`, report source `local-fixture`, and exit code `0`.

Run the intentionally broken fixture separately:

```powershell
npm exec -- paypath test --mode buggy --scenario successful-payment --report .\successful-payment-buggy.json
```

Expected: `FAIL (ENTITLEMENT_NOT_GRANTED)` and exit code `1`. This nonzero result is the expected finding for the buggy fixture; it is not a successful customer integration run. Both fixture commands use an in-memory store and generated billing evidence. They make no Stripe, Supabase, or Demo API request.

The checked-in [Fixed report](examples/successful-payment-fixed.json) and [Buggy report](examples/successful-payment-buggy.json) were generated by these actual commands. They are raw CLI outputs from `local-fixture`, not evidence from a real account. Their `sub_fixture…` and `evt_fixture…` identifiers are generated by the local fixture and are not real Stripe IDs or IDs from prior account tests. Reports include identifiers and evidence; keep real integration reports out of source control and share them only through an approved private channel.

`ENTITLEMENT_NOT_GRANTED` means the billing evidence establishes that access should be active, but persisted entitlement and/or the authorization result says it is not. Other scenario findings include `ENTITLEMENT_NOT_REVOKED` and `DUPLICATE_WEBHOOK_EFFECT`.

## Real Integration configuration

The CLI loads `.env.integration.local` first, then `.env`, from its current working directory. Keep the integration file untracked and out of browser/client bundles. In a customer application repository, first obtain the template from the maintainer as described above, save it as `pilot-integration.env.example` in the repository root, and copy it to `.env.integration.local`. Replace every placeholder locally:

```powershell
if (Test-Path .\.env.integration.local) {
  throw '.env.integration.local already exists; review it before copying the template.'
}
Copy-Item .\pilot-integration.env.example .\.env.integration.local
notepad .\.env.integration.local
```

Required values for `paypath test --integration`:

| Variable | Required value |
| --- | --- |
| `STRIPE_SECRET_KEY` | Stripe Test Mode secret key beginning `sk_test_`; Live keys are rejected. |
| `PAYPATH_STRIPE_SUBSCRIPTION_ID` | Existing test subscription ID (`sub_…`) to inspect. Its Stripe metadata `paypath_user_id` must equal the configured PayPath test user. |
| `SUPABASE_URL` | HTTPS URL of the isolated Supabase project (local development may use localhost). |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-side key for that isolated project. Treat it as a privileged, write-capable credential; it is not a read-only key. |
| `PAYPATH_TEST_USER_ID` | Test user ID beginning `paypath-test-`, matching the Stripe subscription metadata and the persisted Demo data. |
| `PAYPATH_TEST_SUPABASE_REF` | Project ref matching the Supabase URL hostname; use `local` for a local Supabase URL. |
| `PAYPATH_SUPABASE_TEST_PROJECT_ACK` | Must equal the literal `disposable-test-project`. |

`PAYPATH_DEMO_BASE_URL` is optional and defaults to `http://localhost:3000`. Non-local Demo URLs must use HTTPS. Scenario-specific subscription and user overrides are supported as `PAYPATH_STRIPE_SUBSCRIPTION_ID_SUCCESSFUL_PAYMENT` and `PAYPATH_TEST_USER_ID_SUCCESSFUL_PAYMENT` (replace the suffix with the uppercase scenario ID, using underscores). For the duplicate-webhook scenario, `PAYPATH_WEBHOOK_EVENT_ID_DUPLICATE_WEBHOOK` or `PAYPATH_WEBHOOK_EVENT_ID` selects an already-recorded event whose delivery and business-effect rows will be read.

`doctor` checks Node.js and parses available environment configuration; it does **not** contact Stripe, Supabase, or the Demo API. It reports known template values as `INCOMPLETE`; a syntactically valid configuration is reported as `FORMAT VALID` only. Both messages explicitly state that the connection was not tested. The command keeps its informational exit-code contract: configuration being missing, incomplete, or invalid does not by itself make `doctor` return a nonzero exit code; an unsupported Node.js version returns `1`. Therefore, a zero exit code from `doctor` is not proof that credentials work, that the selected project is safe, or that a service is reachable. The CLI validates the `sk_test_` prefix, requires HTTPS for remote Supabase, checks that its URL ref matches `PAYPATH_TEST_SUPABASE_REF`, and requires the explicit disposable-project acknowledgment.

Before scanning, an operator must arrange test data through the Demo application's normal test flow: a Stripe Test Mode subscription, matching `paypath_user_id` metadata, the application's persisted subscription/entitlement state, and a reachable Demo authorization API. The Demo webhook route validates Stripe's signature when it receives an event, but the CLI scan does not itself inspect webhook signatures or prove how a persisted row was created. It does not create a Checkout, subscription, invoice, webhook delivery, or Supabase record. It retrieves the Stripe subscription and latest invoice, selects the matching Demo subscription/entitlement (and, for duplicate-webhook, event/effect evidence), and sends an HTTP `GET` to `/api/pro/feature`.

The scan code issues reads only, but **the required Supabase service-role key is privileged and can write/delete data**. Use a dedicated disposable project, keep the key server-side, and never put credentials in frontend variables, CI logs, Git, Issues, PRs, or reports. The Stripe adapter enforces an `sk_test_` key prefix but does not prove that the key has read-only API permissions; the CLI does not accept a restricted-key prefix today. Treat the key as capable of changing Test Mode objects. The separate `paypath cleanup` command deletes scoped Supabase test rows after an interactive confirmation; it is not read-only and is not part of a scan. The Demo app's Checkout and webhook processing also write test data. This CLI scan does not deliver or replay webhooks.

## Run a real scan

Create a private report directory first. For example, in PowerShell:

```powershell
$reportDir = Join-Path $env:TEMP ("paypath-reports-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $reportDir | Out-Null
npm exec -- paypath doctor
npm exec -- paypath test --integration --scenario successful-payment --report (Join-Path $reportDir "successful-payment.json")
```

The scan is based on pre-existing test evidence. For `successful-payment`, expected evidence includes an active test subscription, paid latest invoice, a matching persisted application subscription, a successfully read entitlement (a confirmed absent row is evidence of no entitlement), and authorization consistent with the billing policy. Use the `cancellation` scenario only when its configured subscription satisfies the cancellation/period-end precondition. `duplicate-webhook` requires an already-recorded event plus its delivery and business-effect rows; the CLI does not generate a duplicate.

Every run writes JSON with `schemaVersion`, `runId`, `generatedAt`, `source`, `results`, and `summary`. A result contains the scenario, status, `errorCode`, expected and actual state, evidence, reproduction steps, and duration. The `source` for a real scan is `stripe-supabase-integration`; local examples say `local-fixture`.

| Status | Meaning | CLI exit behavior |
| --- | --- | --- |
| `PASS` | Complete evidence agrees with the scenario policy. | `0` only when every requested scenario passes. |
| `FAIL` | Complete evidence confirms a policy violation, such as `ENTITLEMENT_NOT_GRANTED`. | `1`. |
| `ERROR` | A scenario adapter/API operation failed or returned an invalid response. | `1` for a reported scenario error. |
| `INCONCLUSIVE` | Required evidence or the billing precondition is missing/unavailable. | `1`; never treated as a pass. |

An integration adapter/configuration error caught while evaluating a scenario is reported as `ERROR` and makes the command exit `1`. An uncaught CLI usage or report-writing exception is sanitized on stderr and exits `2`. A nonzero scan must be diagnosed from the JSON report and service setup; do not rerun automatically or turn missing evidence into a pass. `doctor` is informational and does not set a nonzero exit solely for missing, placeholder, or invalid integration configuration; inspect its explicit status text, and use the integration scan report—not `doctor`—as the execution result.

## Current pilot boundaries

- This is a private pilot package distributed as a local tarball; it is not npm-published.
- Supported evidence is specific to the current PayPath Demo tables and API contract; arbitrary customer schemas and entitlement policies are not discovered.
- Real Stripe Test Mode integration has been exercised by the project team, but each pilot still requires its own isolated test data and verification.
- The Supabase service-role credential is write-capable even though the integration scan's Supabase operations are `SELECT` queries. A deployment that requires a technically read-only credential needs additional adapter support and is a pilot security gap to resolve before granting access to a customer-owned production project.
- The Stripe integration accepts only an `sk_test_` key and performs retrieval calls in the scan, but the CLI does not validate or enforce the key's permission scope. Do not supply a live key; use a dedicated Test Mode account and handle the key as a sensitive credential.
- Local fixtures prove CLI packaging and deterministic policy behavior only; they do not verify Stripe, Supabase, webhook delivery, or customer application behavior.
- GitHub PR Gate uses only local fixtures. It does not run real customer integrations or require account secrets.
